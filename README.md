# Текстовая RPG на Gemini (рабочее название: Game Test 1)

Интерактивная текстовая игра в духе AI Dungeon: игрок задаёт сеттинг и персонажа,
модель Gemini генерирует предысторию мира и ведёт повествование, игрок на каждом
шаге пишет действие или реплику, сюжет реагирует на действие + текущее состояние мира.

**Статус: все 7 этапов готовы.** Игра целиком рабочая: меню с выбором модели, генерация
мира и персонажа, ходы с реакцией сюжета, здоровье и усталость, меняющие поведение
повествования, персонажи с накопительной симпатией, пошаговый бой с локальным расчётом,
журнал и сохранения.
README — это одновременно план и чек-лист выполненного.

**Запуск:** `pip install -r requirements.txt`, затем `python run.py` — откроется
`http://127.0.0.1:8000`.
**Поделиться игрой:** `python run.py --share` — в консоли появится ссылка вида
`http://192.168.х.х:8000`. У каждого, кто её откроет, будет **своя игра**: свой мир,
свой персонаж, свои сохранения. Добавьте `--coop`, если нужна одна общая партия на всех.

> На другом устройстве нужен именно сетевой адрес из консоли.
> `127.0.0.1` и `localhost` означают «этот самый компьютер»: на телефоне такая ссылка
> ведёт в сам телефон, поэтому и появляется «не удаётся установить соединение».

**Игра на сервере, без твоего компьютера:** см. [DEPLOY.md](DEPLOY.md) — образ Docker
готов, там же сравнение хостингов. Игроки заходят по ссылке, вводят пароль и играют
когда угодно, даже когда ты офлайн. Бесплатный вариант без оговорок —
Oracle Cloud Always Free; самый простой — Railway за ~5 $/мес.

**Игра из любой сети:** `python run.py --internet` — поднимается туннель cloudflared
и выдаётся ссылка вида `https://что-то.trycloudflare.com`, которая работает откуда
угодно, хоть с мобильного интернета. Роутер настраивать не нужно. Заодно придумывается
код на вход — без него по ссылке не пустят.

## 1. Ключевые принципы реализации (моё мнение)

Самая важная часть документа: от этих решений зависит, будет игра играбельной или
начнёт «плыть» после десятого хода.

### 1.1. Числа считает код, а не модель

LLM плохо держит арифметику и склонна к дрейфу («здоровье 100 → 87 → 95 без причины»).
Поэтому:

- **Единственный источник правды — локальный объект состояния** (`GameState`, обычный JSON).
- Модель не «помнит» здоровье/усталость/симпатию — они **подставляются в промпт** каждый ход.
- Модель возвращает не новые значения, а **дельты-предложения** (`health: -10`,
  `sympathy: {"Ирма": +5}`), которые код валидирует, ограничивает по модулю и применяет.
- Всё, что считается формулой (урон, попадание, восстановление сил), считает код.

Побочный бонус: состояние тривиально сохраняется и загружается (п.7 ТЗ).

### 1.2. Один ход игрока = один запрос к API

Требование п.8 ТЗ («меньше запросов») выполняется через **structured output**
(`responseSchema` / JSON mode у Gemini): один вызов возвращает сразу всё:

```jsonc
{
  "narrative": "текст сцены, 2-5 абзацев",
  "state_delta": { "health": -5, "fatigue": +12, "time_advance_min": 40 },
  "inventory_changes": { "add": ["ржавый ключ"], "remove": [] },
  "npcs": [ { "name": "Ирма", "role": "торговка", "sympathy_delta": 5, "present": true } ],
  "combat_trigger": { "starts": false, "enemy_name": "", "reason": "" },
  "memory_update": "краткая запись в хронику",
  "suggested_actions": ["...", "...", "..."]
}
```

Никаких «отдельный запрос на описание, отдельный на статы, отдельный на резюме».

### 1.3. Экономия контекста без потери памяти

Слать всю историю дорого и быстро упрётся в лимит. Схема окна:

```
[системный промпт-правила] + [карточка мира] + [хроника (сжатая история)]
+ [состояние: статы, инвентарь, NPC в сцене с симпатией]
+ [последние N = 6-8 ходов дословно] + [действие игрока]
```

Хроника обновляется **в том же самом запросе** (поле `memory_update`), а не отдельным
вызовом суммаризации. Раз в ~20 ходов — одна «уплотняющая» перегенерация хроники;
это единственный дополнительный запрос за сессию.

### 1.4. Усталость и здоровье как «директивы режиссёру»

Просить модель «учитывать усталость» абстрактно бесполезно. Код смотрит на пороги и
**вписывает в промпт жёсткое ограничение**:

- `fatigue > 70` → «Персонаж на пределе. Любая активная попытка (бег, бой, долгий переход)
  должна провалиться или дорого обойтись. Подталкивай сцену к отдыху.»
- `health < 30` → «Персонаж тяжело ранен: опиши слабость, ограничь физические действия.»

Плюс код может **сам отклонять** заведомо невозможные действия, вообще не тратя запрос
(«бежать 10 км» при усталости 95 → короткий локальный ответ «ноги не идут»).
Экономит запросы и делает механику честной.

### 1.5. Симпатия — число со шкалой поведения

`sympathy: -100..+100` на каждого значимого NPC. Код переводит число в ярлык и в
инструкцию поведения, которая идёт в промпт только для NPC, присутствующих в сцене:

| Диапазон | Ярлык | Что требуется от модели |
|---|---|---|
| +60..+100 | Предан | помогает, делится ресурсами, рискует ради игрока |
| +20..+59 | Дружелюбен | охотно общается, мелкие услуги |
| -19..+19 | Нейтрален | торг, безразличие |
| -59..-20 | Неприязнь | грубит, обманывает, завышает цену |
| -100..-60 | Враждебен | активно вредит, может напасть первым |

Порог `<= -60` плюс повод — один из триггеров боя.

### 1.6. Бой — локальная механика, модель только «озвучивает»

Доверять бой целиком LLM нельзя (числа поплывут). Предлагаю:

- Раунд считает код: `урон = max(1, атака + 2d6 - защита)`, с модификаторами от
  усталости и ран. (Изначально была одна кость — заменено после замеров, см. этап 6.)
- Модель вызывается **не каждый раунд**, а по событиям: начало боя, переход HP врага через
  50% и 25%, финал. Реплики врага генерируются **пачкой на старте боя** (4-6 фраз под
  состояния: уверен / ранен / при смерти / побеждает) и дальше выбираются кодом без запроса.
  Итог: ~2 запроса на весь бой вместо 10.
- Экран боя: HP / защита / урон обеих сторон, лог раундов, действия
  «Атака / Защита / Предмет / Бегство».

### 1.7. Ключ API

В `Описание задачи.txt` ключ лежит открытым текстом. Так нельзя: он должен жить в `.env`
(и в `.gitignore`), не в исходниках и не в браузере.
**Рекомендую перевыпустить этот ключ в Google AI Studio**, раз он уже попал в файл.

## 2. Технологический стек

- **Бэкенд:** Python 3.10+ / FastAPI — держит ключ, состояние, механику, ходит в Gemini.
  (проверено на Python 3.10.8; обращение к Gemini — прямой REST через `requests`,
  без официального SDK: меньше зависимостей и предсказуемее поведение)
- **Фронтенд:** одна HTML-страница + vanilla JS (без сборщика), тёмная тема «терминал/книга».
  Запуск: `python run.py` → `localhost:8000`.
- **Хранение:** JSON-файлы в `saves/`, без БД.
- **Почему так:** ключ не утекает в браузер, механику удобно писать и тестировать на Python,
  интерфейс со шкалами и панелями делается в HTML быстро.
  Альтернативы (один HTML-файл без бэкенда / консольное приложение) отпали:
  с ними ключ уехал бы в браузер.

Структура:

```
  game/config.py           # чтение .env, пути, список желаемых моделей
  game/console.py          # UTF-8 и читаемый шрифт в консоли Windows
  game/api/gemini_client.py# REST-клиент: generate_json / generate_text, retry, фильтры
  game/api/models.py       # меню моделей по факту models.list, выбор по умолчанию
  game/api/errors.py       # типы ошибок с готовым текстом для игрока
  game/api/usage_log.py    # учёт запросов и токенов -> logs/api_usage.jsonl
  game/core/worldgen.py    # схема и генерация стартовой карточки мира
  game/core/state.py       # GameState, сериализация, версия схемы
  game/core/rules.py       # дельты, клампы, отдых, пороговые директивы, отказы
  game/core/turn.py        # окно контекста, схема хода, сжатие хроники
  game/prompts/worldgen.md # системный промпт генерации завязки
  game/prompts/gm.md       # системный промпт ведущего для ходов
  game/server.py           # FastAPI: меню, выбор модели, новая игра, ходы
  game/session.py          # своя партия у каждого, кто открыл ссылку
  game/tunnel.py           # выход в интернет через cloudflared
  Dockerfile               # образ для хостинга
  railway.json             # настройки развёртывания для Railway
  deploy/setup.sh          # разворачивание на виртуальной машине одной командой
  deploy/update.sh         # обновление игры на уже развёрнутом сервере
  DEPLOY.md                # инструкция по развёртыванию
  run.py                   # запуск: сервер + браузер
  web/index.html|app.js|style.css  # интерфейс
  game/core/npc.py         # реестр NPC, симпатия, затухание, журнальный фильтр
  game/core/combat.py      # локальный расчёт боя, реплики врага, итог
  game/core/saves.py       # сохранение, загрузка, автосейв, совместимость
  scripts/check_api.py     # проверка слоя API
  saves/  logs/            # сейвы и логи (в .gitignore)
  .env  .env.example  requirements.txt
```

### Этап 4. Статы: здоровье и усталость — ГОТОВО

- [x] Шкалы 0-100 меняют цвет на тех же порогах, на которых меняется поведение сюжета,
      и подписываются словами: «устал», «измотан», «на пределе», «ранен», «тяжело ранен».
      На критическом уровне шкала пульсирует
- [x] Усталость растёт от самого действия (значение от модели) **плюс** естественный износ
      от времени: +1 за каждые 45 минут. Отрицательные значения от модели зажаты до −10,
      чтобы она не «лечила» усталость по своему усмотрению
- [x] Восстановление считает только код (`fatigue_from_rest`): модель лишь сообщает, что
      персонаж делал — поле `rest` со значениями «нет / отдых / еда / сон».
      Передышка — 1 единица за 4 минуты, сон — за 5, еда — фиксированные 8.
      Сон дольше 4 часов вдобавок затягивает раны
- [x] Пороговые «директивы режиссёру» (`state_directives`) вписываются прямо в промпт хода
      блоком «ОБЯЗАТЕЛЬНЫЕ ОГРАНИЧЕНИЯ ЭТОЙ СЦЕНЫ»: усталость от 40 / 65 / 85 и здоровье
      от 50 / 20 процентов дают всё более жёсткие указания вплоть до «любая активная
      попытка ОБЯЗАНА провалиться»
- [x] Локальный отказ без обращения к API (`block_action`): при усталости ≥ 90 или
      здоровье ≤ 12 активное действие получает короткий ответ от кода. Отдых, разговоры
      и наблюдение не блокируются никогда, в сомнительных случаях запрос всё же уходит
- [x] Отказ оформлен как полноценный ход: время идёт, помечен в интерфейсе курсивом
      и красной чертой, подсказки заменяются на «Сесть и отдышаться / Найти укрытие
      и поспать / Достать что-нибудь поесть»
- [x] При 0 здоровья — `game_over`, поле ввода закрывается, кнопка «В главное меню».

### Этап 6. Режим боя — ГОТОВО

- [x] Реплики выбираются кодом по состоянию врага: `confident` / `hurt` (ниже 55 % HP) /

- [x] Выход: победа / поражение / бегство → **один запрос** возвращает историю

**Баланс подобран замерами, а не на глаз** (по 600-800 боёв на вариант). Ключевая правка:
урон считается по формуле `атака + 2d6 − защита`, а не с одной костью. С одной костью
разброс был слишком мал, и исход читался по листу противника ещё до первого удара —
получалась ступенька из 100 % и 0 % побед без ничего между ними.

Итоговая кривая при обычном герое (100 HP, нож, лёгкая защита), тактика «бить в лоб»:

| Противник | Побед | Длина боя |
|---|---|---|
| Задира 40/5/1 | 100 % | 2.8 раунда |
| Вооружённый 75/9/3 | 100 % | 5.1 раунда |
| Боец 95/12/4 | 51 % | 6.3 раунда |
| Опытный 110/13/5 | 0 % | — |
| Чудовище 130/16/7 | 0 % | — |

Усталость решает исход: против одного и того же врага 100 % побед при бодром герое
и 71 % при усталости 95. Бегство — рабочий выход из безнадёжного боя: 65-72 % успеха
даже против чудовища.

**Проверено живой партией.** Боцман полез в драку в кабаке: модель остановила текст
на замахе, бой собрался одним запросом (Борров, 85 HP, тесак), 7 раундов прошли без
единого обращения к API, реплики врага менялись по его состоянию вплоть до
«Небо... чернеет...», игрок проиграл на 5 HP противника, и финальный запрос корректно
описал последствия, не переигрывая исход.

> Честное замечание: «Защита» — не выигрышная стратегия, а способ пережить тяжёлый удар.
> В короткой схватке нападение почти всегда выгоднее, и это видно по замерам.
>
> Бой живёт отдельно от `GameState`, поэтому на этапе 7 он кладётся в сейв целиком:
> сохранение посреди драки восстанавливает её вместе с логом и раундом.

«за столом» с тем, кто сейчас ходит. В обычном режиме эти элементы скрыты.

**Проверено тремя «браузерами» с раздельными куками.** Хозяин, гость 1 и гость 2 получили
разные миры («Каменный Удел», «Океаническая Звезда», «Костяные Пределы»); ход гостя 1
не отразился ни у кого, слот сохранения гостя 1 не виден остальным, метка пережила
перезаход. Отдельно проверен `--coop`: там ход Ани увидел Борис, а при одновременной
отправке прошёл ровно один запрос, второй получил 409.

> Это игра по локальной сети, а не по интернету: ссылка работает для тех, кто в той же
> сети Wi-Fi. Запросы идут по твоему ключу, так что пускать стоит только знакомых.

### Сквозная задача. Экономия запросов (п.8 ТЗ)

- [x] Целевой бюджет: **1 запрос на ход** — соблюдается с этапа 3.

      «Начать игру» запросов не делает вообще
- [x] Никаких фоновых и служебных вызовов модели. Единственное исключение — сжатие

- [x] Счётчик запросов и токенов виден в интерфейсе, полный лог — `logs/api_usage.jsonl`
- [x] Бой: 2 запроса на всю драку вместо запроса на раунд — один на лист врага и запас

## 4. Принятые решения

Согласовано с заказчиком 2026-09-14:

1. **Стек:** Python + FastAPI + браузер. Ключ живёт на бэкенде, интерфейс — локальная
   веб-страница, запуск `python run.py` → `localhost:8000`.
2. **Модели:** при старте приложения делаем один запрос `models.list` по ключу и
   показываем в меню реально доступные Flash-Lite модели.
   **Проверено на этапе 1: все три модели из ТЗ доступны по этому ключу** —
   `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`, `gemini-2.5-flash-lite`
   (всего у ключа 41 модель с `generateContent`). Механизм подбора замены оставлен
   на случай, если модель снимут с обслуживания.
3. **Бой:** кнопки действий «Атака / Защита / Предмет / Бегство», раунд считается локально.
4. **Смерть:** при 0 здоровья — game over с возвратом в главное меню. **Сохранения не
   удаляются**: из меню можно продолжить с автосейва или с любого другого слота.
   Значит, автосейв должен писаться *до* применения смертельного хода, иначе загрузка
   будет сразу возвращать игрока в смерть.
5. **Язык:** только русский. Интерфейс и весь генерируемый текст на русском,
   переключателя языков не делаем. В системном промпте — жёсткая инструкция отвечать
   по-русски.
6. **Контент:** без лишних самоограничений — игра для взрослого single-player, тёмные и
   жестокие сюжеты допустимы. В запросах выставляем `safetySettings` на самый мягкий
   доступный порог (`BLOCK_NONE` по настраиваемым категориям). Важно понимать: часть
   фильтров Gemini отключить нельзя — они применяются на стороне Google. Поэтому нужен
   аккуратный обработчик блокировки: если ответ пришёл с `finishReason: SAFETY`, игра не
   должна падать — показываем короткое локальное сообщение («сцена оборвалась») и даём
   игроку переформулировать действие, **не тратя лишний запрос на автоповтор**.
7. **Ключ API:** остаётся текущий, лежит в `.env` (уже создан, добавлен в `.gitignore`).

## 5. Конфигурация

Созданы:

- `.env` — рабочий файл с ключом (`GEMINI_API_KEY`), моделью по умолчанию, языком и режимом
  фильтрации. **Не коммитить.**
- `.env.example` — тот же набор переменных с пустым ключом, как шаблон.
- `.gitignore` — исключает `.env`, `saves/`, `logs/`, `__pycache__/`, виртуальные окружения.


## 6. Риски

Закрыты по ходу работы:

- **Дрейф состояния** — все числа считает код (1.1), модель предлагает только дельты,
  и каждая зажата в границы.
- **Модель игнорирует усталость** — жёсткие директивы в промпте и локальные отказы (1.4).
  Проверено живой партией: при усталости 88 персонаж не прошёл дальше.
- **Рост контекста и стоимости** — окно из 6 ходов, хроника, затухание NPC (1.3, этап 5).
- **Невалидный JSON от модели** — один ретрай с уточнением, при повторной неудаче ошибка
  наружу и никаких изменений состояния.
- **Неверные id моделей** — `models.list` при старте плюс fallback; все три модели из ТЗ
  доступны.
- **Предрешённый бой** — исправлено на этапе 6 переходом на `2d6` после замеров.

Остаются:

- **Гео-блокировка Google.** Gemini обслуживает не все страны. При запросе из
  неподдерживаемой возвращается `400 User location is not supported` — игра распознаёт
  это отдельно и советует включить VPN. Ключ и код тут ни при чём.
  Хостинг в поддерживаемом регионе снимает вопрос совсем.
- **Фильтры Gemini.** `BLOCK_NONE` выставлен, но часть фильтров отключить нельзя.
  Обработка есть, и всё же на очень жёстких сценах модель может отказать; это ограничение
  Google, а не игры.
- **Расхождение текста и состояния.** Модель иногда описывает потерю предмета, забыв
  указать его в `inventory_changes`. В промпте есть прямое требование, но полностью это
  не лечится — только сверкой инвентаря в журнале.
- **Партия живёт в памяти сервера.** Перезапуск `run.py` теряет текущую сессию; вернуться
  можно через автосохранение.
- **`--share` открывает игру всей локальной сети.** Кода по умолчанию нет: кто угодно
  в той же сети, зная адрес, начнёт свою партию и потратит твою квоту. Для домашнего Wi-Fi
  это нормально, для кафе — нет; там стоит добавить `--code`.
- **`--internet` открывает игру всему интернету.** Адрес случайный и нигде не публикуется,
  плюс закрыт кодом, но это не защита от того, кому ссылку переслали дальше. Квота твоя,
  так что зови только знакомых и гаси игру, когда наигрались.
- **Гости живут на куке.** Очистил куки — потерял доступ к своей партии и сохранениям
  (файлы остаются на диске, но найти их сможет только хозяин).

## 7. Что можно доделать дальше

Ни один из пунктов не входил в ТЗ — это заметки на будущее:

- панель журнала показывает хронику целиком; при очень долгой партии её стоит свернуть
  по главам;
- бой всегда один на один — групповых стычек нет;
- «Защита» в бою уступает нападению по эффективности (см. замеры в этапе 6);
- выбор модели действует на сеанс и не сохраняется в `.env`;
- код на вход один на всех гостей и живёт до перезапуска: отозвать его у одного
  человека нельзя, только сменить для всех;
- адрес туннеля меняется при каждом запуске — постоянная ссылка потребовала бы
  учётной записи Cloudflare и своего домена;
- расход по ключу общий: счётчик в интерфейсе показывает сумму по всем гостям,
  разбивки по игрокам нет;
- гостевые партии живут в памяти сервера и выгружаются через 6 часов простоя.
